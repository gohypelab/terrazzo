# Example App — CLAUDE.md

This is the Terrazzo example app, used for testing the gem's install flow and running system specs. It has its own git repo (separate from the parent Terrazzo repo) to track a resettable **base state**.

## Base state vs generated state

The app ships in a **base state** — a Rails app with models, build tooling, and test specs, but NO Terrazzo admin panel. Running `terrazzo:install` generates the admin panel on top of the base.

**Base state (tracked by inner git):**
- `app/models/` — ActiveRecord models
- `db/` — schema, seeds, migrations
- `package.json` — npm deps and build scripts
- `esbuild.config.mjs` — JS bundler config
- `components.json`, `jsconfig.json` — shadcn/path config
- `config/routes.rb` — bare Rails routes (no admin namespace)
- `spec/` — factories and system specs
- `Gemfile` — with `terrazzo` gem from local path

**Generated by `terrazzo:install` (NOT in base state):**
- `app/dashboards/` — dashboard definitions
- `app/controllers/admin/` — admin controllers
- `app/views/admin/` — React views, components, fields, UI
- `app/views/layouts/admin/` — admin layout
- `app/javascript/admin/` — JS entry point, Redux store, slices
- `app/assets/stylesheets/admin.css` — Tailwind theme
- Admin routes in `config/routes.rb`

## When to reset the example app

Reset the example app (`script/reset_example_app` from repo root) when:
- You want to test the `terrazzo:install` generator from scratch
- The generated files have drifted or become inconsistent
- You're debugging the install flow and need a clean slate
- Before running the install generator to verify it works end-to-end

Do NOT reset when:
- You're running unit tests (`bundle exec rspec spec/lib/`) — they work against the base state
- You're iterating on generated frontend code and want to keep your changes
- You're in the middle of debugging a system spec failure

## When to generate the admin panel

```bash
cd spec/example_app
bin/rails generate terrazzo:install admin --bundler=esbuild
npm install && npm run build
```

Run this after a reset, or when you want to test the full install flow. The generator will:
1. Create the admin application controller and layout
2. Generate JS entry point, store, slices, visit helper, page mapping
3. Run the views generator (React components, fields, UI primitives)
4. Run the routes generator (add admin namespace)
5. Auto-discover models and generate a dashboard + controller for each

## Post-install state

`terrazzo:install` should leave the example app in a buildable, runnable state without hand repairs. The current generator flow handles:

- Admin namespace routes and namespace root route
- Enum-backed attributes as `Field::Select`
- Active Storage and Action Text user-facing field types
- Grouped navigation data through dashboard navigation hooks
- App-level field/component/UI barrels for local overrides
- Shared page mapping plus `generated_page_mapping.js` for resource-specific pages and `custom_page_mapping.js` for manual pages

System specs add deliberate customization coverage on top of that generated state. Those customizations include ejected pages, ejected fields, a custom layout, custom row/header/toolbar actions, custom navigation grouping, and custom dashboard hooks.

## When to change the gem source (`lib/`)

Change files in `lib/` (at the repo root) when:
- Fixing or adding field types (`lib/terrazzo/fields/`)
- Changing the dashboard DSL (`lib/terrazzo/base_dashboard.rb`)
- Changing query logic (search, filter, ordering)
- Changing what the generators produce (`lib/generators/terrazzo/`)
- Changing engine controllers or views (`app/` at repo root)

After changing gem source, run `bundle exec rspec spec/lib/` from the repo root. If you changed a generator, reset the example app and re-run `terrazzo:install` to verify.

## When to change the npm package (`npm/`)

Change files in `npm/` (at the repo root) when:
- Changing utility functions (`cn`, `truncate`, `formatDate`, etc.)
- Changing hooks (`useIsMobile`, `useAppSelector`)
- Changing the field registry API
- Changing store helpers

After changing the npm package, rebuild it (`cd npm && npm run build`) and then rebuild the example app assets (`cd spec/example_app && npm run build`).

## When to change files in the base state

If you need to change a base state file (model, seed, factory, build config, etc.):
1. Make the change in the example app
2. Commit it to the **inner** git repo: `cd spec/example_app && git add -A && git commit -m "description"`
3. Stage the change in the **outer** repo too — the outer repo tracks these files

The inner repo commit is the new base state that `script/reset_example_app` restores to.

## Key differences from a normal Rails app

- No admin namespace exists until you run the generator
- `CustomerDashboard` used by unit tests lives in `spec/support/test_dashboard.rb` (at the repo root), NOT in this app
- The `terrazzo` gem is loaded from `path: "../.."` (repo root)
- The `terrazzo` npm package is loaded from `file:../../npm`
- `esbuild.config.mjs` has a dedupe plugin to handle the local npm symlink
- System specs require the admin panel to be generated and assets built first
